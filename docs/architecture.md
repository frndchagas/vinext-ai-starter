# Architecture

## Overview

The browser will see a single origin. A proxy will forward each path to the correct service:

```text
https://app.example.com                    Caddy
  |
  +-- /                         -> Vinext on Node
  +-- /api/*                    -> Laravel
  +-- /sanctum/*                -> Laravel
  +-- contracted Fortify routes -> Laravel Fortify
  +-- /api/broadcasting/auth    -> Laravel
  +-- /app/* and /apps/*        -> Laravel Reverb, preserving the path
                                      |
                                      +-- PostgreSQL
                                      +-- Redis / Horizon
                                      +-- AI providers
```

Vinext handles the interface, presentation routes, and the user experience. Laravel is the source of truth for identity, authorization, domain, persistence, queues, and events. The same-origin topology avoids a fragile cookie and CORS setup and must be the same in development, E2E, and production. The frontend will use relative URLs and will not know the internal service ports.

## Frontend

The frontend will be created with `create-vinext-app` and will have:

- React and App Router;
- TypeScript with `strict`, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes`;
- Tailwind CSS 4 via the official Vite plugin;
- shadcn/ui with Base UI, components copied into the repository, and Tailwind CSS;
- TanStack Query for remote state;
- Zod only at boundaries that receive external data;
- HTTP client generated by Orval;
- MSW generated from the same OpenAPI contract;
- Laravel Echo to receive events from Reverb.

There will be no manual HTTP calls inside components. Screens use the generated `api-client` package, and presentation components know nothing about authentication or transport details.

## Backend

The backend will follow the conventional Laravel structure:

- thin controllers;
- Form Requests for input;
- API Resources for output;
- Models and Services for business rules;
- Jobs for asynchronous work;
- Events for observable transitions;
- Policies and Gates for authorization;
- Spatie Laravel Permission for persisted roles and permissions;
- enums for domain states;
- Horizon for Redis workers;
- Reverb for WebSocket;
- Laravel AI SDK for AI integrations with structured output.

Custom interfaces appear only at real external boundaries, such as AI providers, the clock, and remote storage. The starter will not create abstractions without a second concrete implementation or a clear testing need.

## Authentication

The SPA flow will be:

1. The browser obtains the Sanctum CSRF cookie and the client sends its decoded value in the `X-XSRF-TOKEN` header.
2. Fortify handles registration, login, password recovery, and email verification.
3. Sanctum recognizes the first-party session on HTTP calls.
4. Echo uses the same session on the `/api/broadcasting/auth` endpoint.
5. `routes/channels.php` checks the User and the resource before granting access to a private channel.

Personal tokens will not be used by the main browser. 2FA, passkeys, social login, and teams come after version 0.1 but remain in the plan as documented extensions.

## Type-first HTTP contract

TypeSpec will be the canonical source for every HTTP boundary visible to the frontend, including authentication. Its compiler will emit OpenAPI 3.1. Orval will generate types, `fetch` functions, TanStack Query hooks, the required Zod schemas, and MSW handlers.

Prism will validate requests and responses of the Laravel implementation. Oasdiff will detect incompatible changes between the published version and the proposed one. CI will also recompile TypeSpec and regenerate the artifacts in a temporary directory; any unversioned difference will fail.

```text
TypeSpec
   |
   +-- OpenAPI 3.1 --> Orval --> TypeScript, Fetch, Query, Zod, and MSW
   |
   +-- Prism --------> validation of the Laravel implementation
   |
   +-- oasdiff ------> breaking-change detection
```

oRPC, tRPC, and ts-rest are out because the server is PHP. They would not eliminate the HTTP contract and would add a second representation to maintain.

## Queues and real time

Long-running operations will follow a single pattern, detailed in [Queue reliability](queue-reliability.md):

1. Laravel validates the request and persists a resource with an initial state.
2. The job is dispatched after the transaction commits.
3. The worker processes the job with persisted idempotency, three attempts, a 120-second timeout, and backoff of 10 and 60 seconds.
4. Each relevant transition is persisted before broadcasting.
5. Reverb sends only a notification for the frontend to refresh or invalidate the query.

The WebSocket event will not be the source of truth. If the connection drops, the browser will recover the current state through the HTTP API. Public channels, events, and payloads will be described in AsyncAPI.

## Observability

Each request will receive a correlation ID. The same identifier will flow through logs, jobs, and Reverb events. Errors will have structured context, without secrets, and integration tests will verify the propagation of this ID in the example flow.

## Local services

Docker Compose will have, at minimum:

- `proxy`;
- `postgres`;
- `redis`;
- `api`;
- `queue`;
- `reverb`;
- `web`;
- `mailpit` in the development profile.

Each service will have a healthcheck. Bootstrap will wait for dependencies to become healthy before migrating or starting tests.

## Deployment target

The target for version 0.1 will be Node in a container for Vinext, with separate containers for the API, worker, and Reverb. Cloudflare Workers will be reevaluated only after the main flow is stable and covered by E2E.

## Starter boundaries

The starter delivers infrastructure and a small vertical example. It will not include business rules for a specific SaaS, billing, a marketplace, a credit system, or a closed design.
